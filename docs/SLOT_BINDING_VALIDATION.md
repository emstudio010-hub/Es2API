# 账号槽位归属校验

## 2026-11-06 源码增量

此增量在 `v2026.11.06-preview.30` 之后，修改 integration 生命周期校验；r30 Linux 归档不包含此增量，二进制和 UI 没有变化。

控制面读取槽位时，除核对固定槽位 ID 和执行后端，还必须确认：

- `isolation.account_id` 与操作账号相等。
- `isolation.generation` 是大于零的安全整数，且与该账号当前 `provision_generation` 相等。

任一项缺失、无效或不匹配，返回 `409 vm2_slot_binding_mismatch`。不会因为槽位 ID 相同或状态为 running，就继续接管、导入凭据、checkpoint、启停、恢复或删除。这也适用于创建响应丢失后查找已存在槽位的路径。只验证预期 ID、尚未读取槽位的本地检查不构成归属确认，后续读取仍须通过完整检查。

不完整的历史记录不会自动补写归属。原账号、凭据和已知槽位 ID 保留，管理员应检查原记录及实际归属。槽位明确返回 404 时，原有创建/删除重试规则继续适用。

## 当前证据边界

本次只做源码审查、语法检查、仅模块加载、服务重启和现有非 pending 槽位的只读状态清点；没有进行模型调用、OAuth 换票、槽位创建/删除、故障注入、并发操作或测试套件。因此不能据此宣称不完整元数据分支已通过行为验收。

自动 IP 分配已在地理位置查询之后同步预留，并拒绝同一代理资源行被多个托管槽位占用。本次没有改动代理存储：`ProxyPool` 仍保留内存工作集，`ProxiesRepo.replaceAll()` 全量写入 SQLite；尚未证明多个控制进程同时写同一数据库时的安全性。不同代理资源也可能共用供应商公网出口，资源独占不等于经过验证的公网 IP 独占。这些边界仍需后续处理。

真实 Codex CLI→API 的最近一次授权调用仍以 `codex_cli_connection_failed` 结束，未取得有效正文或 usage。此校验增量不代表连接问题已经解决。
